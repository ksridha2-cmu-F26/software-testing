1. Why were test doubles necessary?

SocialNetwork uses an AccountDAO for data storage, but the real database is not available. The fake let me test the application quickly without a database. Mocks and spies also let me check that SocialNetwork called the DAO correctly.

2. Advantages and disadvantages

- Fake: easy to use and realistic, but it required more code to implement.
- Mock: useful for checking DAO method calls, but it needed more stubbing.
- Spy: combined the fake's behavior with Mockito verification, but still depended on the fake's implementation.

3. Faults found

- SocialNetwork needed dependency injection so it could use test doubles instead of the incomplete real DAO.
- AccountDAOFake needed to store cloned accounts and support update and delete operations.
- Account had bugs in blocked-request handling and equality.
- SocialNetwork had bugs in unblocking, leaving, persisting accepted or rejected requests, and filtering recommendations.
- The mock and spy tests needed DAO setup and real verification statements.

4. Suggestions

A setup helper for selecting the DAO double would make the tests easier to read. An example of a stateful Mockito mock would also be helpful.
